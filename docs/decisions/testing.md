The legacy application had no tests at all, so the harness is new ground and I wanted it to be trustworthy, not just green: a test that has only ever passed could be checking the code or checking nothing, and you cannot tell which by looking at it. The architecture rules were the clearest case. They are enforced by ArchUnit and say things like "the domain imports no Spring or database types", but a setting from when they were written, before the code they guard existed, still told ArchUnit to treat "found nothing to check" as a pass, so a rule that silently stopped matching after a package rename would have passed forever. I switched that back to strict, gave the one rule that is legitimately empty until the JPA adapter lands an explicit exemption with the issue number beside it, and added a small package of deliberately wrong classes, kept in the test sources so the real gate never sees them, each breaking exactly one rule. A test feeds the real rule objects those classes and asserts that every rule complains and names the offender, with one rule the fixtures respect checked to stay quiet so the proof is about the rules and not the loader. The same idea runs through the other gates: a test pins the running context to the MongoDB container it started, and the docs record a drill per gate with the captured failure text. The point I would make in an interview is that the test suite is the executable specification of what the legacy app did, and a specification you have never seen reject anything is not one you can defend; making each gate fail on purpose, once, and keeping that proof in the build is the difference between "the build is green" and "the build is green and that means something".
