The catalog can run on either MongoDB or a SQL database, and I want to be clear that this is not me hedging about which one to use. MongoDB is the choice. It is the default, it is what starts when you run the app with no arguments, and the customer side of the application, the part I would call the headline of the migration, only exists there. Under the SQL profile you cannot even sign in. What the second implementation is for is evidence. The whole argument for moving this application to documents is that the old catalog kept one product across six tables and had to join all six to draw a single product page, and that as a document it is one read. On its own that is a sentence on a slide and you have to take my word for it. So the SQL side deliberately rebuilds the 2003 schema: the same six tables, the same column names, right down to five separate columns for what should be a list, because the old design had no way to store a list either. Now the comparison is not MongoDB against some other database, it is the old data model against the new one, both running, and anyone can watch the joins disappear. Two things came free with it. The first is that it keeps the new code honest. The business objects are meant to be plain Java with nothing database-specific in them, and a second implementation is what turns that from a claim into something that breaks if it stops being true; a stray database annotation in the wrong package failed the build the same afternoon I wrote it. The second is that it is the reversibility story. A real migration does not burn the boats on day one, it keeps the old store working until the new one has earned its place, and here that is a flag at startup. It costs perhaps a quarter more work on the catalog and it is the first thing I would drop if I ran out of time, but the same twenty-five tests pass against both stores, which is the strongest form of the argument I can make.
