The old catalog was seven SQL statements and a JSP bean called `CatalogHelper` that you configured one property at a time ,start, count, locale, the search box , before asking it for a page. I kept the seven operations and dropped the mutable bean: `CatalogService` takes its parameters, so two requests can never share a half-set object the way a session-scoped `<jsp:useBean>` could. The paging looks naive at first glance because it slices a list in memory instead of pushing skip and limit into the database, but that is exactly what the legacy did ,every statement ran unbounded and the DAO then scrolled the cursor to the start row and read `count` rows off it ,so this is parity rather than a shortcut, and it is honest about a catalog of twenty-eight items. Three oddities fall out of that loop and I kept all three, each pinned by a test that says so in as many words: asking for zero rows gives you one, because the loop adds a row before it first checks the count; paging past the end loses the Previous link as well as Next, because the shared empty page was built with a start of zero and knows nothing of the start you asked for; and Previous steps back by the current page's size, so coming off a short last page you step back short and re-read a row. Three other things I changed on purpose. The legacy ordered categories and products by name but ordered items and search results not at all, which is not something you can page over ,page two only means anything relative to a page one cut from the same order ,so items and search results are sorted by id, and the old app only got away with the omission because one database happened to return rows in insertion order. Locale used to be a join condition, so a row with no translated half simply fell out of the result set; now that the translations are embedded per document nothing falls out on its own, so the service filters explicitly, and there is still no fallback to English because there never was one. And searching for "Angelfish" with a capital A returned nothing in 2003 ,the shipped DAO lower-cased the column but not the pattern it compared against ,so I lower-case the keywords, which is what the other, disabled DAO in the same package already did. That last one is a defect fixed rather than a behaviour preserved, and writing it down here instead of quietly correcting it is the distinction I would want to be judged on: everything above is either the legacy behaviour with a test naming the line it came from, or a departure with a reason.
