The legacy app shipped its catalog as an XML file and a servlet: hit `/Populate?forcefully=true` and it dropped the six catalog tables, recreated them and streamed `Populate-UTF8.xml` back in through a chain of SAX filters, one per table. I wanted the same thing for the new app, but as a document import rather than a table fill, and I wanted it to be checkable rather than just "data appeared". So the issue has three parts and a test on each side of it.

The data first. I did not hand-write a JSON fixture, because a fixture someone typed is a second copy of the seed with no proof it matches the first. Instead a small script reads the original `Populate-UTF8.xml` from the reference tree and writes `src/main/resources/seed/catalog.json`; I run it, commit the output, and never edit the JSON by hand. It is deterministic, so if the file ever changes in a diff it means the transform changed, not the data. The transform itself is the interesting bit: the six tables (category and category_details, product and product_details, item and item_details) become three collections, and the per-locale detail rows that used to hang off each entity by a foreign key are embedded under `details` keyed by locale. That is the relational-to-document step a real migration would do with a mapping tool, done by hand at a size where you can read the whole thing. Two details of the old loader survive on purpose. The seed writes `xml:lang="en-US"` but the loader stored `en_US`, because that is what `Locale.toString()` gives and what the DAO queried with, so the keys are underscored. And nothing fills gaps: `EST-15` has no Japanese row in the seed, so it has no Japanese row here either, and the counts are 28 / 27 / 28, not 28 / 28 / 28. Prices stay as strings in the fixture because deciding between `BigDecimal` and `Decimal128` belongs to the catalog domain, which comes later, and a seed should not make that call for it.

Then the loader, which is one small class in the Mongo adapter behind a property. Switch the property on and it drops the three collections and inserts the fixture on startup; leave it off and it does not exist. That is `forcefully=true` with the check step removed: drop and reload is idempotent, and idempotent is the property you want from something you will run right before a demo. It writes raw documents rather than domain objects because at this point in the plan the catalog domain has not been written, and I did not want the seed to wait on it; when the catalog adapter lands it adopts this shape rather than the other way round. It is Mongo only for now, which is a gap I am writing down rather than hiding: the JPA adapter for the catalog is a later, cut-candidate issue, and until it exists there is no relational catalog store to seed.

And the test, which is really two. One reads the legacy XML directly from the reference tree and pins what it contains: five categories, sixteen products, twenty-eight items, the per-locale counts, the missing Japanese row, the underscore locale keys, every product pointing at a real category and every item at a real product. It is tagged as a parity test because it describes the old app, not the new one, and if it ever fails either the reference tree was touched or the reader stopped reading the seed the way the servlet did. The other boots the app against a real MongoDB container with the property on, lets the loader run twice, and asserts the collections hold exactly what the first test read from the XML. Same counts, same locale keys, same gap. The acceptance criterion for the issue is "same counts per locale as the legacy seed, one command reloads", and the point I would make in the interview is that both halves of that sentence are executable: the counts are compared against the legacy file itself, not against a number I remembered, and the one command is a script that a reviewer can run.
