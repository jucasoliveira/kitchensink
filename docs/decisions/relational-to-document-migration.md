# Moving the data: relational → document

**Issue:** 7.5 (#47) · **Anchors:** finding #2 — no authoritative DDL exists for the CMP tables

The acceptance criterion for this issue is deliberately narrow: *"mapping rules and how a real
engagement would move the data, not a hand-written script."* A script written against a schema
nobody can produce would be theatre. What follows is the mapping, the reason a script is the wrong
artefact here, and the approach an actual engagement would use.

---

## 1. Start with the problem: there is no source schema

Finding #2. The Pet Store CMP tables were **generated by the container** from `<cmp-field>`
declarations and the `<relationships>` block. The tree contains:

- `ejb-jar.xml` per component — field names and relationships, no types, no keys, no indexes
- `PopulateSQL.xml` — `CREATE TABLE` for the **catalog** tables only, which were plain JDBC and
  never CMP
- nothing at all for `customer`, `account`, `contactinfo`, `address`, `creditcard`, `profile`,
  `user`, `purchaseorder`, `lineitem`, `inventory`, `counter`

So for the tables that matter most, the column names, types, nullability and indexes existed only
inside a 2003 application server's generated schema, and they varied by container. **You cannot
write a correct migration script from this repository**, and anyone who hands you one has invented
the schema.

This is not a curiosity — it is the single most important fact about migrating this application,
and it generalises: *a CMP/AUTO-generated schema is a migration input you have to recover from a
running system, not from source control.*

---

## 2. The mapping rules

These hold regardless of what the generated column names turn out to be, because they are derived
from the CMR graph, which *is* in source control.

| Legacy construct | Becomes | Rule |
| --- | --- | --- |
| CMP entity that is an aggregate root (`CustomerEJB`, `PurchaseOrderEJB`) | a collection | one document per row |
| CMR `1:1` marked `<cascade-delete/>` | embedded subdocument | ownership is already declared |
| CMR `1:1` not marked, but the target is never addressed alone | embedded subdocument | check the home interface: no finder ⇒ not addressable |
| CMR `1:Many` where the many side has no independent identity (`LineItemEJB`) | embedded array | bounded by a human action |
| CMR `1:Many` where the many side *is* addressed directly (`product`, `item`) | separate collection + reference | `GET_ITEM` takes an `itemid` |
| Side table keyed by `(parent_id, locale)` (`*_details`) | `Map<locale, …>` inside the parent | never read except through the parent |
| Entity bean declared in *n* `ejb-jar.xml` files (`AddressEJB` ×5) | **one** value type | the duplication was a packaging artefact, not a model |
| `<prim-key-field>` | `_id` | keep the natural key; do not add an ObjectId beside it |
| Separate credential entity joined on the natural key (`UserEJB`) | a field on the same document | the join existed because CMP had no other way |

Two rules that matter more than they look:

- **Keep the natural key as `_id`.** `userId` is the primary key, so it *is* the document identity.
  Adding a generated `ObjectId` and keeping `userId` as an ordinary field costs a second unique
  index and — more importantly — loses the duplicate-account refusal for free, which is exactly
  what `MongoCustomerRepository.add` relies on.
- **An absent value and an empty value are different.** A nullable column becomes an absent key,
  not `""` or `null`. `CustomerRepositoryContract` has three assertions that exist only to hold the
  two adapters to the same answer on this, because it is where they most easily diverge.

## 3. How a real engagement would move it

Not a script. Four phases, in this order:

**1. Recover the schema from a running instance, not from source.**
Point a JDBC introspection tool at the legacy database and dump the actual DDL — column names,
types, nullability, foreign keys, indexes. This is the deliverable that does not exist in the repo
and cannot be reconstructed from it. Everything downstream is written against *that*, not against
`ejb-jar.xml`.

**2. Characterize before you move.**
The parity tests in this repository are the pattern: pin what the legacy answers *before* changing
where it answers from. Reads first — they are safe to run against production — and the assertions
become the acceptance criteria for the migrated store. This slice has 39 such assertions running
against both stores; a real engagement would have them per aggregate.

**3. Move with a change-data-capture tool, not a batch job.**
The realistic mechanism is dual-write or CDC (Debezium onto the relational binlog, MongoDB
Relational Migrator for the schema mapping), running while the legacy system stays live:

- take an initial snapshot, transformed by the rules in §2
- stream ongoing changes so the document store stays current
- run both stores in parallel and **compare reads** — the port/adapter split makes this cheap,
  because the comparison is one interface with two implementations
- cut over per aggregate, not per application

A one-shot ETL script requires an outage proportional to the data size and gives no way back. CDC
gives an arbitrarily long verification window and a rollback that is just "stop reading from the
new store".

**4. Cut over one aggregate at a time.**
The order matters and it is the reverse of the dependency graph: aggregates that nothing references
go first. Here that would be catalog (read-only, no writes to reconcile), then customer, then
orders. Each cutover is a profile switch — which is precisely what `scripts/profile-switch.sh`
demonstrates in miniature.

## 4. What this repository actually demonstrates

Honestly stated, because the difference matters:

| Demonstrated here | Not demonstrated here |
| --- | --- |
| The mapping rules, applied to two real aggregates | Moving production data |
| Both stores answering one test suite (39 assertions) | CDC, dual-write, or a cutover |
| Aggregate boundaries recovered from `<cascade-delete/>` | Recovering the generated DDL — no instance to introspect |
| A rollback path (`--spring.profiles.active`) | Rollback with data written to the new store |

The seed data here comes from `Populate-UTF8.xml`, copied verbatim
(`LegacySeedCopyIsVerbatimTest`), so the catalog migration *is* a real transformation of real
legacy data — 5 categories, 16 products, 28 items, 4 locales — just not a large or a live one. The
customer aggregate has no legacy data at all; the CMP tables were created empty and populated by
the running application.

See [`document-design.md`](document-design.md) for the target shapes and the numbers behind them.
