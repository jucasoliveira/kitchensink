# 09 — What I learned, and how I would run the next one

**Issue:** 8.4 (#52) · Answers the brief's third playback bullet directly.

Written as things that changed my mind during the work, not as a list of good practices I already
believed. Each one has a place in this repository where it bit.

---

## 1. The schema you have to migrate is not in the repository

The single most consequential thing I found, and I found it late enough to have wasted time on the
assumption that it was there.

Pet Store's CMP tables were **generated by the container** from `<cmp-field>` declarations. There
is no DDL for `customer`, `account`, `contactinfo`, `address`, `creditcard`, `profile`, `user`,
`purchaseorder`, `lineitem`, `inventory` or `counter` anywhere in the tree. `PopulateSQL.xml`
creates the *catalog* tables, and only because those were plain JDBC and never CMP. Column names,
types, nullability and every index existed only inside a 2003 application server's generated
schema, and varied by container.

**What that means:** you cannot write a migration script from the source repository, and anyone who
hands you one has invented the schema. The mapping *rules* are recoverable from `<relationships>`
— which is in source control — but the source shape has to be introspected from a running system.

**Next time:** get read access to a running instance and dump the real DDL in week one, before
writing a line of target code. Treat "we have the source" and "we have the schema" as unrelated
claims. This is now §1 of
[`decisions/relational-to-document-migration.md`](decisions/relational-to-document-migration.md).

## 2. The legacy configuration already knows where the aggregate boundaries are

I expected to have to *decide* the document boundaries. I mostly had to *read* them.

`<cascade-delete/>` on a CMR relationship is the legacy saying "this is owned" — and it is exactly
the aggregate boundary. `components/customer/src/ejb-jar.xml:280` and `:343` draw the customer
aggregate. The multiplicity element tells you embed vs. reference. The *home interface* settles the
remaining cases: if a bean has no finder, nothing addresses it directly, so it embeds.

The corollary is the more interesting half. The catalog's `*_details` tables look identical in
shape to the customer's value tables — a side table keyed on the parent — but they are
one-per-locale, a real collection, and the JPA adapter deliberately **rebuilds** them as tables
while the customer's values become flat columns. Same-looking legacy artefact, two different
answers, and the difference is recoverable from the configuration rather than guessed.

**Next time:** start from `<relationships>` and the home interfaces, not from the table list. The
table list is the container's opinion; the relationships are the modeller's.

## 3. Characterization tests are the only thing that made the scope cut safe

ADR-0006 cuts cart, checkout and the order workflow. The reason that was defensible rather than
reckless is that the *rules* were extracted and pinned first — 177 tests tagged `parity`, each
naming the `file:line` it preserves — so "not built" is a statement about code, not about
understanding.

The specific technique that paid: **write the assertion against the legacy source before writing
any target code.** `CreditCardTest` pins that `getExpiryMonth()` returns `"01"` and
`getExpiryYear()` returns `"2010"` when the date has no slash. Those are hardcoded literals in a
2003 bean and were already three years expired when it shipped. Nobody would reimplement that from
a spec, and a migration that silently "fixed" it would be changing behaviour under cover of a port.

**Next time:** same, but earlier. I wrote the parity harness in E2 and it should have been E1 — the
walking skeleton and the characterization suite want to land together, because the skeleton is what
proves the harness can run and the harness is what makes the skeleton worth extending.

## 4. A test that has only been seen green may be testing nothing

Three separate instances in this repository, and the third one changed how I write tests.

- `RulesCanFailTest` exists because an ArchUnit rule that matches no classes passes. It evaluates
  the real rules against fixtures written to break them.
- Two tests asserted the database held *exactly* one collection. Both passed for a year on **test
  ordering** — the catalog suites share the Testcontainers instance. Adding one new test class
  shifted the order and both went red. They were never asserting what they claimed.
- The profile-switch script's first version deleted `./target/surefire-reports`, but `pom.xml`
  redirects the build elsewhere. The second run read the first run's reports and reported perfect
  agreement between a profile and itself — 47 "shared" assertions including three that exist only
  on one side.

That last one is the sharpest: **a demo that cannot fail proves nothing**, and mine briefly
couldn't. The fix — ask Maven where the directory is rather than reconstructing the path — is
trivial. Noticing was not.

**Next time:** for every gate, write the drill that makes it red *in the same sitting*. Not later,
not "if there's time". The cost is minutes and it is the only thing that distinguishes a gate from
a decoration.

## 5. Ordering bugs between framework lifecycle hooks are invisible by default

Issue 7.3 cost two wrong attempts and both were instructive:

- `@PostConstruct` created the catalog indexes at bean initialisation — and the seeder's
  `dropCollection`, running much later as an `ApplicationRunner`, dropped them again. Every read
  went back to a full scan while the class that was supposed to prevent that sat there looking
  correct.
- `ApplicationReadyEvent` failed *differently*: `@SpringBootTest` stops short of publishing it,
  while runners still execute. So the seeder worked in tests and the indexes did not — **green in
  tests, indexed in production, and no way to tell from either**.

Only `explain()` found it. "The index exists in the source" and "the planner chose it" are
different claims, and the gap between them is invisible at this data size.

**Next time:** assert on the query plan, not on the index declaration, for anything that matters.
And be suspicious of any lifecycle hook whose behaviour differs between `main()` and
`@SpringBootTest` — that difference is where a whole class of bugs lives.

---

## 6. Port/adapter earns its keep at the *second* adapter, not the first

Writing `CustomerRepository` with one Mongo implementation felt like ceremony. It stopped feeling
that way the moment the JPA adapter landed, because the 15 assertions in
`CustomerRepositoryContract` transferred **for free** — six lines of configuration in a subclass —
and immediately caught real divergences: `save()` vs `persist()` for the duplicate rule, and a null
column vs an absent key for the optional field.

The honest version of this: the abstraction is not justified by "we might swap the store one day".
It is justified by the fact that **it makes the migration verifiable**. Two adapters answering one
suite is the only evidence that the application above the port is genuinely store-agnostic, and
that evidence is what a stakeholder actually wants before agreeing to a cutover.

**Next time:** build the second adapter early even if it is throwaway, purely as a verification
device. H2 cost about two hours here and is the single strongest artefact in the deliverable.

## 7. How I would run the next one

In order, with the changes above folded in:

1. **Week zero, before any code.** Introspect the running system for the real schema. Inventory the
   deployment units and the configuration files, not the classes — `ejb-jar.xml`, `web.xml` and
   their equivalents hold the model. Count the duplication; it is usually the clearest number you
   will get (25 declarations for 13 beans, here).
2. **Cut scope explicitly and write down the argument.** One vertical slice, end to end, beats
   breadth every time — a slice forces every target-stack decision to become real, and a broad
   port defers all of them. Park the deferred work as *closed* issues in a separate milestone so
   nobody mistakes it for backlog.
3. **Walking skeleton and characterization harness together**, not sequentially.
4. **Ports first, second adapter early**, as a verification device rather than a feature.
5. **Every gate gets its drill in the same sitting.** Coverage floor, ArchUnit rules, parity tags,
   the profile-switch demo — each one needs a demonstration of what red looks like.
6. **Migrate data with CDC, not a batch script.** Dual-run and compare reads through the port; cut
   over one aggregate at a time, in reverse dependency order.
7. **Keep the decision trail as you go.** ADRs superseded rather than edited, a decision note per
   slice as it lands. Reconstructing *why* three weeks later is lossy, and in a migration the "why"
   is most of the deliverable — the code is the easy part to re-derive.

## 8. What I would do differently in *this* repository, given another day

- **The `_class` discriminator.** Spring Data writes
  `_class: "…adapter.persistence.mongo.CustomerDocument"` into every document. That pins an adapter
  class name into stored data: rename or move the mapping type and existing documents stop reading.
  It should be turned off or pinned to a stable alias, and I would not have noticed it if the demo
  rehearsal had not put a raw document on screen.
- **`CatalogIndexes` builds indexes in the foreground at startup.** Correct at 28 items, wrong
  against a live collection. It needs `background: true` or to move out of the application
  entirely.
- **`GET /api/customers` returns a 302 to `/login`** rather than a 401, because `formLogin` owns
  the entry point for the whole chain. A separate API-scoped `SecurityFilterChain` is the fix.
- **The JPA customer adapter has no schema test.** Deliberate — JPA is a verification device here,
  not a deliverable — but it is a gap and it should be named rather than discovered.
